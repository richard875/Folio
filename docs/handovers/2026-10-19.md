## 1. Outcome and user decisions

The repository now has **one shared resource tree under `.claude/`**. Both Claude
Code and OpenCode can discover its skills. No `.agents/` mirror, symlink arrangement,
copying script, or synchronization workflow is needed.

The user initially had a large unstaged migration that removed `.grok/` and created
two substantially identical trees: `.claude/` and `.agents/`. The perceived need
for both was support for Claude Code and OpenCode. The user requested investigation
and a proposal before implementation, then approved the single-source approach
with an explicit condition: verify duplicates before removing anything.

The approved implementation was completed, checked, and subsequently committed at
the user's request. The user then requested this detailed repository handover.
This handover and its documentation-index entry are not part of `b87b656`. They
were initially drafted without committing. The user subsequently authorized a
sensitive-information review and a separate documentation commit, but not a push.

### Why `.claude/` was retained

- Claude Code discovers project skills from `.claude/skills/`.
- OpenCode V2 also discovers `.claude/skills/` natively as a compatibility source.
- The existing `opencode.json` already loaded `.claude/references/*.md`.
- Folio's in-progress migration already directed runtime configuration and logs to
  `.claude/`; choosing that tree avoided a second runtime relocation.
- `.agents/skill-copies/` was deliberately named so OpenCode would not discover
  it. The mirror supplied no additional discovery coverage for either tool.

The folder name is a supported shared location, not a claim that the files are
Claude-only. Moving everything to a neutral third directory would have added
configuration or linking work without solving an additional requirement.

Local artifacts can coexist under `.claude/`, including ignored `dev.log`,
`app-env.json`, preview files, and an optional brand-task marker. They are not
second copies of the tracked resource collection.

### Project instructions versus references versus skills

1. **`AGENTS.md`:** authoritative project-wide constraints. OpenCode loads it
   directly. Root `CLAUDE.md` contains only `@AGENTS.md`, using Claude Code's import
   syntax rather than duplicating the instructions. The import also supports
   Claude Code versions/sessions that do not load `AGENTS.md` directly.
2. **`.claude/references/`:** supporting repository workflows. OpenCode explicitly
   loads all Markdown files there through `opencode.json`. Claude Code can read
   the same guides when project instructions or the task call for them; the import
   in `CLAUDE.md` does not itself import every reference.
3. **`.claude/skills/`:** discoverable task-specific packages. Discovery exposes
   metadata; it is not a reason to load every skill body for every task.
4. **`docs/skills/universal-article-reader/SKILL.md`:** the current Folio-specific
   article-reader workflow. It remains in its existing documentation location;
   this change did not relocate it into the optional App Builder skill library.

## 5. Runtime paths and legacy compatibility

### Environment precedence

Use the existing npm scripts; do not run Vite directly. The wrapper in
`scripts/with-app-env.mjs` resolves flags in this order, with later values winning:

1. Tracked `.claude/app-env.defaults.json`.
2. Optional ignored `.claude/app-env.json`.
3. Process environment.

Only string-valued `VITE_` entries are accepted from the JSON files. They are flag
carriers, not secret stores. `ACCESS_HASH`, proxy credentials, and private tokens
must not be moved into these files or any `VITE_` variable.

There is one intentional compatibility exception: **if the new override is absent
with `ENOENT`**, the wrapper can read an existing `.grok/app-env.json` as a read-only
fallback over the canonical defaults. It does not recreate a `.grok/` resource
tree, and it does not fall back when a new override is unreadable for another
reason. A present but malformed new JSON document parses to no overrides rather
than selecting the legacy file.

`.gitignore` retains protective legacy entries for `.grok/` artifacts and
`.agents/app-env.json`. Those entries protect accidental local files; they do not
mean either resource tree should be restored. Do not remove secret-protection
ignore rules merely to eliminate every textual mention of an old directory.

### Development and production contracts remain unchanged

- Node: **24.20.0**, with `>=24.20.0 <25` required by `package.json`.
- Start development with `sh startup.sh`; it probes the existing service and
  launches `npm run dev` only when needed. It remains idempotent and non-blocking.
- Development binds `0.0.0.0:8080`; QA preview uses `127.0.0.1:8081`.
- `npm run preview:restart` uses Linux `/proc` behavior; do not use it as a macOS
  process-manager workaround.
- Active deployment remains one Render Free Node service in Singapore with

- Storage remains private temporary files under `output/`; do not delete or

- `VITE_AUTH_ENABLED=false` disables optional account scaffolding, not Folio's

Some inherited template comments still describe hosted-platform behavior that is

The executable defaults, Render configuration, and `AGENTS.md` govern Folio.

## 6. Tests, maintenance implications, and limits

The new `scripts/agent-resources.test.mjs` contains four contract tests:

1. **Inventory and preservation:** checks real resource files, the exact skills
   and references inventories, and normalized SHA-256 preservation against the
   original `.grok/` migration manifest. The original README is excluded from the
   content checksum comparison because discovery documentation changed.
2. **Discovery metadata:** checks all 18 expected directories, matching lowercase
   skill names, descriptions, frontmatter presence, and uniqueness.
3. **Shared configuration:** checks the exact `CLAUDE.md` import, OpenCode's
   reference glob, absence of the duplicate `.agents/` resource locations, and the
   auth-off default.
4. **Documentation paths:** checks selected current guides for obsolete mirror
   instructions and verifies concrete canonical paths, excluding examples and
   optional local artifacts.

The root of `.claude/` is deliberately not frozen to an exact file inventory;
future tool settings and ignored local artifacts can coexist there. The resource
subtrees are exact inventories, and substantive edits to original resources will
currently fail preservation checks. When intentionally changing or adding skills
or references, review and update the inventory/checksum policy deliberately along
with the change. Do not silently regenerate expected hashes just to conceal an
unexpected failure. The manifest's old `.grok/` source label is provenance, not a
current runtime path.

These tests verify repository contracts, not a launched end-to-end discovery test
inside both external clients. Documentation for both tools was consulted during
the proposal; fresh Claude Code and OpenCode sessions were not launched solely
to prove their user-facing skill menus. Installed/global skills may also affect
which definition a particular session selects.
